## Bugs found (and fixed) during this phase

1. **`create_subscription`'s concurrency gap.** `select_for_update()` only
   locks rows that already exist; when a user has no live subscription yet,
   two concurrent `create_subscription()` calls both pass the Python
   pre-check and race to `INSERT`, so the second one raised a raw
   `django.db.utils.IntegrityError` instead of the intended
   `DuplicateSubscriptionError`. Caught this via the real-Postgres
   concurrency test (it would never have surfaced against SQLite, since
   SQLite doesn't enforce the constraint under concurrent writers the same
   way). **Fix**: `create_subscription` now catches `IntegrityError` from
   the `uq_subscription_one_live_per_user` constraint and re-raises it as
   `DuplicateSubscriptionError`, so callers get one consistent exception
   regardless of which layer caught the race. The DB constraint remains the
   real safety net; the Python check is now correctly understood as an
   optimization, not the source of truth (documented inline in the code).
2. **My own test bug** in an early draft of
   `test_two_concurrent_renewals_do_not_double_extend_period`: it computed
   an expected value from a stale in-memory object after a real renewal had
   already mutated the DB row, which produced a `current_period_start ==
   current_period_end` state that correctly tripped
   `ck_subscription_period_end_after_start`. Rewrote the test to compute the
   expected post-renewal value via `billing_utils.compute_period_end`
   directly rather than re-deriving it from a stale object. Documented here
   per the instruction to report bugs found and fixes even when found in the
   verification work itself, not just production code.
3. **Pre-existing Phase 2 test-ordering fragility**: see
   `PHASE_3_FORENSIC_FINDINGS.md` §6 —
   `test_entitlement_concurrency.py`'s `setUp` depended on migration-seeded
   `Plan` data surviving an earlier, unrelated `TransactionTestCase`'s table
   flush. Fixed with a one-line, behavior-neutral `get_or_create` change; no
   Phase 1/2 production code was touched.

No other bugs were found. Regression across all pre-existing Phase 1/1A/1B/2
tests: **zero failures, zero new skips beyond the pre-existing Postgres-gated
ones**, on both SQLite and real PostgreSQL.

## Remaining limitations (honestly disclosed)

See `PHASE_3_SUBSCRIPTION_ARCHITECTURE.md` §12 for the full list:
plan-change/upgrade-downgrade is architecture-ready but not implemented
(out of scope per Step 15); the one-live-subscription-per-user constraint is
scoped per-user rather than per-`(user, plan)` (a deliberate simplification
given this project has exactly one paid plan today); no periodic background
sync job exists yet (reads are still always correct per Step 12, this is
purely a "how fresh is the DB row between reads" optimization); the grace
period deadline lives in a JSON `metadata` field rather than its own column.

None of these bear on correctness, security, or the completion gate
requirements below — all are pre-existing-scope or explicitly-deferred
items, not defects.
